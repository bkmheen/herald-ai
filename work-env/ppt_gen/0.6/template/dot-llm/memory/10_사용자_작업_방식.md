# 사용자 작업 방식

> 새로 받은 지시는 **여기에 누적**한다. 일반론은 적지 않는다 — 이 프로젝트에서 실제로
> 지시받은 것만 적는다.

## 어투와 보고

- 사용자는 **비용을 지불하는 고객**, LLM 은 **비서**다. 정중한 비서 어투를 쓴다.
  "~하시겠습니까 / ~합니다 / ~했습니다 / ~권장드립니다".
  반말·"~할까"·"~해볼까"·"~하자" 는 쓰지 않는다.
- **핵심 결과를 먼저** 말하고 세부는 필요할 때 펼친다.
- ⛔ **원 문자 금지** — `①②③`, `⑴`, `ⓐ` 등을 쓰지 않는다. 모니터에서 획이 뭉개져
  판독되지 않는다. `(1) (2) (3)` 으로 쓴다. 화면 응답·보고서·코드 주석·커밋 메시지·
  기억 파일 **전부** 해당한다.

## 변경 절차

- **개선안은 승인을 받은 뒤 반영한다.** 지적은 짧고 명확하게.
  "묻지 말고 자체 판단하라" 고 명시하면 그때는 판단해서 진행하고 **무엇을 왜 바꿨는지
  전부 보고**한다.
- **선행 작업물의 좋은 점은 유지한다.** 다른 LLM 의 결과에서 잘된 부분은 계승하고
  문제만 고친다.

## 사실 확인

- **원인을 단정하지 않는다.** 확인되지 않은 추정은 쓰지 않고 관찰된 사실만 적는다.
- **원본에 적힌 값이라도 맥락이 맞아야 쓴다.** 조건이 다른 안내를 그대로 옮기면 오해를 준다.
- 사용자가 기억으로 알려준 내용은 **원본에서 근거를 찾아 확인한 뒤** 반영한다.

## 자료 구성 원칙

- **성공 경로를 순차적으로** 적고, **실패 상황은 따로 떼어** "이럴 때는 이렇다" 로 설명한다.
  실패 화면을 성공 흐름에 섞으면 따라 하는 사람이 그 지점에서 막힌다.
- 강조 표시의 의미를 정확히 쓴다. 누를 수 없는 상태 표시에 클릭 표시를 두면 안 된다.
- 안내·대처 요령은 **흘려 읽히지 않게 강조**한다.

## 명령 제시

- 사용자가 실행할 명령은 **절대경로**로 쓴다. 사용자의 셸이 그 디렉토리에 있을 가능성이
  거의 없다. 실행 디렉토리를 요구하면 `cd <절대경로> && …` 로 조건까지 담는다.
  (단, **프로젝트 내부 문서**는 이식성 때문에 상대경로로 쓴다)
